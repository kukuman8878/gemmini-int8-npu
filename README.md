# gemmini-int8-npu

**用 SystemVerilog 从零写了一个"专门算矩阵乘法的电路"，并用真实数据证明：它能翻译成真电路、算得对、面积速度都量得出来。**

---

## 一句话 + 一组硬数字

> 一个人算几百万道矩阵乘法太慢？找 16 个"小计算员"站成 4×4 方阵，数据像心跳一样一拍一拍地在方阵里流动，大家一起同时算——这就是**脉动阵列**。这个项目把它写成了电路，还给了真金白银的实测数据：

| 指标 | 实测值 | 大白话参照 |
|---|---|---|
| 电路面积 | **83774 µm²**（≈ 0.084 mm²） | 约等于十几根头发并排的横截面 |
| 最慢路径 | **7.32 ns** | 1 纳秒 = 十亿分之一秒；眨一下眼约 1 亿纳秒，这电路算一步只要 7 纳秒 |
| 目标时钟 | 100 MHz（每秒 1 亿次"心跳"，每次 10 ns） | 7.32 就算完，还剩 2.68 ns 富余 |
| 验证 | 18 个回归目标全绿、15 条真实 bug 闭环、coverpoint 28/28 | "考试全过，还抓了 15 个错题并订正" |
| 端侧对照 | 小米 10 跑 MobileNetV2 INT8，CPU 推理 **9.16 ms** | 1 毫秒 = 千分之一秒；比一次心跳长 100 万倍，尺度不同，别混着比 |

> **口径红线（很重要，先说清）**：上面三类数字**不能互相换算**——手机 9.16 ms 是真实设备物理耗时，7.32 ns 是电路里一步的时序，83774 µm² 是软件预估的面积。三者分别来自"手机实测 / 电路仿真 / EDA 估计"三条完全独立的路径。全文所有数字都只在自己那条路径内比较，不跨尺度吹牛。

## 这是什么？（30 秒看懂）

先说清楚两个词，后面全靠它们：

- **矩阵**：一张填满数字的表格。**矩阵乘法** = 拿两张表，按规则算出一张新表，过程里要做海量的"两个数相乘、再把结果累加"。
- **位（bit）**：信息的最小单位，一个 0 或 1。**INT8** 就是"每个数字用 8 个 0/1 来表示"，位越少越省面积省电、但能表示的数越小。

一个人算太慢，怎么办？答案是**找一群人站成方阵**：

- 每个人只负责结果表格里的**一个格子**
- 数据像流水线传送带一样，一拍一拍地传过每个人手里
- 轮到谁，谁就把手上两个数相乘、累加到自己负责的格子里，然后继续往下传

因为数据"像心跳一样有节奏地跳动"（英文 systolic = 心脏收缩），所以叫**脉动阵列**。这个项目里，那"一群人"就是 **16 个"小计算员"（行话叫 PE）** 排成的 **4×4 方阵**，外加一个安排大家干活顺序的**调度器（controller）**。

这个项目做的四件事：

1. 用 SystemVerilog（一种"用代码描述电路"的语言）把方阵写成电路
2. 在电脑上模拟它运行，证明算得对
3. 把代码翻译成真实的**门电路**（芯片里最基础的"开关零件"，比如"两个开关都开才通电"的与门），量出面积和速度
4. 跟权威开源项目 **Gemmini**（伯克利大学的 AI 加速器）对比，结果一致

## 快速开始（照抄即可）

前提：装好工具（方法见 [TUTORIAL.md](TUTORIAL.md) 第 3 节），并且已经 `git clone`（"下载代码"）到本地。下面每条命令原样敲进去、回车即可，开头都是 `make`——"帮我执行后面这件事"。

```bash
# 第 0 步：进入项目目录（clone 之后）
cd gemmini-int8-npu

# 第 1 步【必须】检查代码有没有低级错误（像作文查错别字），结束无 Warning/Error 即通过
make lint

# 第 2 步【必须】跑全部 18 个测试目标，最后显示 "REGRESSION PASS"（英文："测试全通过"）
make regress

# 第 3 步【必须】跑一个完整大任务（含 8 个小场景），最后显示 "TESTS=8 PASS=8"
make sim_top
```

**看到什么算对：**

| 命令 | 期望输出 |
|---|---|
| `make lint` | 没有任何 `Warning` / `Error` |
| `make regress` | 最后一行 `REGRESSION PASS`（约 1~2 分钟） |
| `make sim_top` | 最后一行 `TESTS=8 PASS=8 FAIL=0` |

<details>
<summary>想深入：这三步背后分别在证明什么？</summary>

## 关键结果（每一阶段都有实测证据）

### 一、面积和速度（来自 EDA 实测，非估算）

我们的电路在 100 MHz 时钟下能正常工作。先解释单位：**100 MHz = 每秒 1 亿次"心跳"，1 秒 = 10 亿纳秒，所以每次心跳只有 10 纳秒**。

| 指标 | 数值 | 大白话 |
|---|---|---|
| 面积 | 83774 µm² | 约 0.084 mm²，约十几根头发并排的横截面 |
| 最慢路径 | 7.32 ns | 电路里最慢的一条计算路要花的时间 |
| 余量（slack） | 2.68 ns | 每拍 10 ns，7.32 就算完，还剩 2.68 富余；**正数 = 来得及** |

> 证据在哪：`synthesis/reports/` 下 `npu_top_sv_stat.rpt`（面积）、`npu_top_sv_sta_full.rpt`（时序）。复现命令见文末"复现说明"。

**三种优化对比（诚实记录，含"翻车"案例）：**

| 方案 | 最小时钟周期 | 面积 | 结论（一句话） |
|---|---|---|---|
| 基线 | 7.32 ns | 83774 µm² | 作为参照 |
| carry-save（CSA） | **6.13 ns** | 125965 µm² | 提速 19%，但面积贵 50%，性价比偏低 |
| carry-select | 6.90 ns | 83468 µm² | 几乎没收益，白忙一场 |
| CSA + 输出流水 2 级 | 7.78 ns | 134349 µm² | **负收益**，比基线还慢，如实记录 |

<details>
<summary>完整 PPA 表 + 术语解释（进阶）</summary>

**PPA** 是衡量芯片好坏的三项指标：**Power（功耗）、Performance（性能）、Area（面积）**。本项目没做功耗（缺功耗库，见"局限"），只给了性能 + 面积。

**carry-save / carry-select 是什么？** 数字电路里做加法，最慢的部分是"进位"——个位算完，进位要传给十位，十位算完再传给百位……像一串人接力传话。carry-save 和 carry-select 都是"怎么让这个接力更快"的两种技巧。我们用通俗方式理解即可，细节看 `docs/05_ppa_sta_report.md`。

| 方案 | 面积 µm² | WNS @10ns | 最小时钟周期 | 可达频率 | 说明 |
|---|---|---|---|---|---|
| 基线 | 83774.10 | 2.68 | 7.32 ns | ~137 MHz | 瓶颈是 32 位累加器进位链 |
| CSA + 输出流水 1 级 | 125964.56 | 3.87 | 6.13 ns | ~163 MHz | 频率 +19%、面积 +50%、总延迟 -16% |
| carry-select | 83467.55 | 3.10 | 6.90 ns | ~145 MHz | 收益微小（-0.4% 面积） |
| CSA + 输出流水 2 级 | 134348.85 | 2.22 | 7.78 ns | ~128 MHz | **负收益**（+7% 面积、还更慢） |

**诚实结论**：这个 4×4 阵列的固有瓶颈是"32 位累加器的进位链"（约 7.3 ns）。我们试了两种优化，一种要拿 50% 面积换 19% 速度（不划算），一种几乎没用。还如实记录了一个"负收益"方案——**不是所有优化都成功，失败也要写清楚**。完整分析（含根因、口径、可达频率扫描）见 `docs/05_ppa_sta_report.md`。

> 口径说明：以上为**综合后（pre-layout）**数据，工艺库 sky130（公开的 130 纳米工艺库），时序由 OpenSTA 读出；不是布局布线后的流片数据。这是软件预估的下限参考，真实流片会略有差异。

</details>

### 二、验证闭环（证明"算得对"）

**思路一句话**：用 Python（一种写程序的语言）**独立**算出标准答案，再和电路结果**逐元素比对，必须一模一样**（整数运算就该完全精确，差 0.01 都算 bug）。

| 证据 | 实测 | 大白话 |
|---|---|---|
| 回归目标 | **18 个全绿** | 18 场考试全过 |
| 真实 bug | **15 条闭环** | 抓到 15 个错，每条都有"现象→原因→修复→复测通过"完整记录 |
| 功能覆盖率 | coverpoint **28/28** | 计划要测的 28 种情况全部覆盖到 |

<details>
<summary>15 条 bug 都是什么？（很有学习价值）</summary>

分三类，见 `docs/08_bug_log.md`（每条含触发用例、根因、修复 commit、回归确认）：

- **设计缺陷**（2 条）：如同拍配置+启动会误用旧配置、done 信号脉宽不对。
- **测试基座缺陷**（6 条）：尤其精彩的是 3 个"假绿"——比如测试脚本的退出码写错导致"仿真失败还打印 PASS"、en 门控测试用 0×0=0 掩盖了 bug。
- **环境/工程缺陷**（7 条）：如 make 目标命名冲突、源文件改了不重编译、Icarus 对符号数的截断 bug 等。

还有更狠的：**突变验证**——故意往电路里注入错误，看测试能不能抓出来（`make fault_inject`）。抓不出来就说明测试有盲区，再补测试。这一套下来，才敢说"18 个全绿"是**真绿**，不是测试写得宽松。

</details>

### 三、跟官方 Gemmini 对比（证明"理解是对的"）

Gemmini 是伯克利大学开源的 AI 加速器（用另一种叫 Chisel 的语言写的）。我们把同样的矩阵乘法喂给它和我们自己的电路，结果一致。还顺带测出两个重要结论：

| 发现 | 实测 | 大白话 |
|---|---|---|
| 官方基线 | **PASS** | 我们搭建的官方环境跑官方测试，通过 |
| 数据流差异 | WS 比 OS **快 56%**（2268 vs 3550 cycles） | 换一种"搬运数据的方式"，同样的活少花 36% 的周期 |

<details>
<summary>WS 和 OS 是什么？为什么这个结论有意义？</summary>

矩阵乘法有几种"数据在阵列里怎么流动"的走法：

- **OS（输出静止，Output Stationary）**：结果格子固定不动，A、B 流过来。**这是我们自研电路用的方式。**
- **WS（权重静止，Weight Stationary）**：权重先固定好，输入流过来算。Gemmini 运行时两种都能选。

同一组 64×64×64 的矩阵乘法，实测 OS 用 3550 个周期、WS 只用 2268 个周期——**WS 快 56%**。这量化了"数据流选择"这个架构决策的代价，也正好回答了"为什么我们选 OS"——**选 OS 是为了电路简单、好理解、好验证，不是因为它最快**。详细分析（含口径，避免误读）见 `docs/06_gemmini_comparison.md`。

> 口径：周期数含数据搬运、配置、fence 全流程，是"端到端"周期，不是纯阵列计算周期。且 Gemmini 是 16×16 阵列 + 完整 SoC，我们自研的是 4×4 计算子系统，**层次不同，不把原始数值做等价对比**。

</details>

### 四、真实手机实测（证明"能落地"）

在**小米 10** 手机上，跑真实的 **MobileNetV2**（一个常用的图像识别模型）INT8 版本，用 CPU 后端推理一次：

| 指标 | 实测 | 大白话 |
|---|---|---|
| 推理延迟 | **9.16 ms**（3 组，各 110 次，极稳定） | 识别一张图约 9 毫秒，约 1 秒 100 张 |
| 后端 | CPU（XNNPACK，4 线程） | 用的是手机 CPU，不是专用 NPU（没测到） |

更有说服力的是：把模型里**真正要算的那一步 1×1 卷积**（图像识别里的核心计算）抽出来，映射成矩阵乘法，喂给三个地方对答案：

| 谁算的 | 结果 |
|---|---|
| Python（标准答案） | 基准 |
| 我们自研的 4×4 电路 | 5120 个元素，**0 个不一致** |
| 官方 Gemmini（16×16） | 784 个元素（N=16 子集），**0 个不一致** |

**三方完全一致**。这意味着我们的电路不是玩具——它能把真实 AI 模型里的一步，算得和权威实现一模一样。

> 证据在哪：`reports/mobile/`（手机原始日志）、`benchmarks/phone_layer_01/`（真实层数据）。注意：9.16 ms 是整次识别的总时间，7.32 ns 只是电路里一步，尺度差百万倍，**不冲突也不可比**。

## 诚实披露局限（单独一节）

这个项目**没有做到**的事，我们大大方方列出来，不藏着掖着：

| 局限 | 说明 | 大白话 |
|---|---|---|
| 单 tile 只有 4×4 | 一次只能算 4×4 大小的块，大矩阵要在测试端切块 | 只有 16 个"小计算员"，人不够多 |
| K ≤ 256，超了要分块 | 累加维度（每个格子累加多少次）最多 256，更大要切成多段累加 | 累加次数有上限 |
| 无片上存储 | 数据由测试端一拍一拍喂进去，没有内置存储器缓存 | 电路"不记东西"，喂一口算一口 |
| 无功耗库，不报功耗 | 缺少工艺的活动率和功耗库数据，所以 PPA 只给了 P（性能）和 A（面积），没给 P（功耗） | 没量过的坚决不编 |
| 综合后数据，非流片 | 面积/时序是 pre-layout 预估，不是布局布线后的真实流片数据 | 是"图纸估算"，不是"造出来实测" |

**没做的功能**：没有 bias / ReLU / 量化缩放（输出保持精确整型）、没有内置全尺寸 GEMM 调度器（切块在测试端）、不做跨时钟域。完整清单见 `docs/07_known_limits.md` 和 `docs/01_requirements.md` 的"明确不做"。

## 复现说明（给想自己动手的人）

**跑仿真（前面已给）**：`make lint` → `make regress` → `make sim_top`，装好 `iverilog` + `verilator` + `cocotb` + `numpy` 即可。

**跑综合 / 时序【可选】**（量面积和速度才需要）：

```bash
# 第 0 步：装好 synth 环境（一次性，见 TUTORIAL.md 第 3.2 节）
conda create -n synth -c litex-hub python=3.8 yosys open_pdks.sky130a
conda install -n synth -c litex-hub openroad

# 第 1 步：激活环境
conda activate synth

# 第 2 步：一键跑综合 + 时序分析，报告生成在 synthesis/reports/
make synth
```

**Gemmini 对照【进阶可选】**：环境搭建见 [GEMINI_SETUP.md](GEMINI_SETUP.md)。

> 所有性能数字都来自工具实际跑出来的报告（`synthesis/reports/`、`reports/mobile/`、`logs/gemmini/`），不预填、不估算。
